# EE-AUDIT-Rules_Emerging — Reglas emergentes de auditoría documental

**Propósito:** acumular **reglas detectadas durante la auditoría** de cada documento del Engineering Ecosystem, **antes** de decidir si ya están cubiertas por un documento normativo (EE-DOC / EE-ADR / EE-RFC) o si faltan y deben incorporarse por cambio gobernado.

**Uso:**

1. Durante la auditoría de un documento, si surge una regla (convención, prohibición, excepción, SSOT), se **registra aquí**.
2. Al **cerrar el ciclo de auditoría** del conjunto documental, se revisa esta lista:
   - **Cubierta** → ya está en EE-DOC-00x (u otro normativo) con referencia.
   - **Falta** → proponer incorporación (Tipo A / B / ADR / RFC según EE-DOC-005).
3. Este archivo **no es normativo** por sí mismo. Es inventario de auditoría en `docs/validation/audit/`.

**Relacionados:**

- `EE-AUDIT-Criteria_Audited_Definition.md` — qué significa “auditado”
- `EE-AUDIT-Log_Progress_Register.md` — progreso por documento

**Convenciones de esta tabla:**

- **ID:** `AR-YYYY-NNN` (Audit Rule, año, correlativo)
- **Origen:** documento auditado + hallazgo / observación
- **Estado:** `Registrada` | `Cubierta en norma` | `Pendiente de norma` | `Rechazada` | `Diferida`

### Cómo añadir una regla nueva

1. Asignar siguiente ID `AR-2026-NNN`.
2. Redactar la regla en una frase normativa clara (prohibición / obligación / excepción).
3. Citar **origen** (documento + sección o ID de hallazgo).
4. Estado inicial: **Registrada**.
5. No inventar cobertura: marcar **Cubierta en norma** solo con referencia verificable a EE-DOC/ADR/RFC.

## Pendientes para próximos documentos (backlog de auditoría)

Inventario de **trabajo diferido** que se ejecuta al auditar / editar cada artefacto (o el documento indicado). **No** forma parte del paquete actual salvo lo ya materializado en norma.

**Prefijos de ID por sección (obligatorio — no mezclar):**

| Sección | Prefijo  | Ámbito                                                               |
| ------- | -------- | -------------------------------------------------------------------- |
| **A**   | `PC-NNN` | Por cada documento del **corpus** (al auditarlo)                     |
| **B**   | `PN-NNN` | Documentos **normativos** concretos (006/010/015, RFC-003, skill, …) |
| **C**   | `PA-NNN` | **Automatización** (gates, CI)                                       |
| **D–E** | —        | Orden de trabajo y procedimiento (sin ID de pendiente)               |

**Campo Cumplido:**

| Valor       | Significado                                                      |
| ----------- | ---------------------------------------------------------------- |
| **No**      | Pendiente                                                        |
| **Parcial** | Norma lista o algunos docs hechos; falta corpus o automatización |
| **Sí**      | Cerrado con evidencia (doc/§ o PR)                               |

Al cerrar un ítem: poner **Sí**, fecha y referencia (documento auditado, PR, commit).

### D. Orden sugerido de auditoría (referencia)

1. Cerrar **PN-005** (RFC-003) con el merge del paquete documental pendiente.
2. Seguir orden de índice **EE-DOC-003 → … → 015** (y ADR/RFC/IMP/TEC asociados).
3. En **cada** documento: bloque **A** (`PC-001`…`PC-010`) según hallazgos.
4. En **006 / 010 / 015**: bloque **B** (`PN-001`…`PN-004`).
5. **PA-001** cuando toque automatización.
6. **PN-006** (skill) cuando se priorice tooling.

### E. Cómo actualizar el cumplimiento

1. Tras auditar un documento, recorrer `PC-001`…`PC-010` (y `PN-*` / `PA-*` si aplica).
2. Si el criterio de cierre se cumple **para ese doc**, anotar en **Evidencia** (ej. `EE-DOC-004 vX — 2026-10-12`).
3. **Cumplido = Sí** solo cuando el alcance completo del ítem está cerrado (no un solo archivo, salvo ítems de un solo documento como PN-001).
4. **Parcial** si la norma está lista pero el corpus no (ej. PC-001 mientras queden IMP/TEC).
5. **No reutilizar** el prefijo de otra sección (p. ej. no insertar un `PC-` en la sección B).
